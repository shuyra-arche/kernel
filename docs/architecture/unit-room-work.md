# Unit、Room 与 Kernel Work 设计推导

本文记录 Shuyra Kernel 的目标模型。讨论已确认两项决定。**共享访问由 Nest 的映射表达，授权由 Pend 表达，Share 不作为独立概念。Kernel Work 是 Kernel Nest 下的普通 Unit，既不是 Unit 的子对象，也没有独立 Task 类型。**

「设计约束」说明目标模型需要保持的性质。生命周期表示、交接顺序和 Rust 片段均为候选，尚未经实现验证。调用权限、失败结果与编码以现行 [Kernel API](../../api/README.md#callable-interfaces) 为准。

## 一、概念推导

### 从控制流到物理执行

一条独立控制流在创建、暂停、等待、迁移和结束期间需要可识别的身份。**Unit** 持有这个身份和终结事实。**Room** 决定何时让它参与执行、在哪里就绪或等待，以及当前能否占用某个 Hart。一次抢占或迁移只改变执行位置和调度记账。接受结束决定后，Unit 负责将结束推进到可观察的完成。

**Hart** 是 RISC-V 的硬件执行线程。**Metal** 保存和恢复该 Hart 上的架构现场，处理陷入、寄存器、地址转换上下文和必要的硬件同步。Room 选择下一控制流，Metal 将选择落实为硬件执行。逻辑位置提交、硬件恢复和旧现场可回收各有自己的证据。

### 从内核例程到 Kernel Work

Kernel Work 运行在 Kernel Nest 下，用普通 Unit 的身份和生命周期承担内核职责，例如推进退出清理或发现内存退役进度。长期 Work 可以处理多次独立输入。每次提交沿用该 Unit 的身份和生命周期。就绪工作耗尽时，Work 可等待并交还 Hart，后续由 Room 重新派发。

待处理记录、退役进度与在途硬件义务由各机制保留。Work 在自己的控制流中推进这些机制的有界步骤。Work 让出、等待或退出时，已经接收的责任需要由原所有者继续结清或明确移交。

### 从请求到数据、地址、权限和通知

- **Copy** 创建并交付独立副本。交付后，源缓冲区的修改或释放不改变副本。接收方也可以通过受授权的 Nest 映射读取该副本。
- **Nest** 表达地址映射。Flat 组织逻辑存储，Cell 提供底层存储。同一 Cell 区间可在多个 Nest 中映射到不同地址，各映射分别保留访问与退役责任。
- **Pend** 表达哪一个主体可对哪一个目标执行哪些操作，且可限制范围。派生权限受有效祖先约束。取得授权、发布映射、撤回访问和硬件退役各有完成条件。
- **Sign** 负责事件观察、通知和一次等待的裁决。通知可以合并。接收方醒来后，向数据或结果的所有者重查可领取状态。
- **Input / Output** 是纯数据在创建、一次操作或 Unit 终结中的角色。同一份数据可以先作为 Output，再作为另一个操作的 Input。数据身份与存续责任来自值本身或承载它的既有资源。

这里沿用本分支对物理所有权、逻辑占有与地址访问的区分。[Cell、Flat 与 Nest 目标设计](../design/memory.typ)

## 二、责任边界

| 概念 | 持有的事实和责任 |
| --- | --- |
| Unit | 控制流身份、创建发布、结束决定、终结结果，以及与自身身份绑定的退出义务。 |
| Room | 逻辑执行位置、Hart 参与、就绪选择和调度记账。协调派发、让出、抢占、等待和退出时的位置提交。 |
| Kernel Work | 以普通 Unit 的控制流推进内核机制。相应机制保留队列、游标、重试记录及未结清义务。 |
| Hart / Metal | Hart 的硬件身份与可信状态。Metal 管理架构现场、陷入与恢复，提供时钟、中断与所需硬件同步。 |
| Sign | 事件观察状态、确切的等待登记，以及该次等待由事件、超时、取消或来源关闭哪一方结清。 |
| Copy | 独立副本的建立与交付，明确提交前后由谁持有数据。积压存储与领取是否属于通用 Copy 合同仍待确定。 |
| Nest | 地址占用、映射安装及发布、撤回，并在旧访问结清前保留相应责任。 |
| Pend | 当前有效的授权、派生谱系、范围及撤销。资源授权与 Unit 管理资格各自核对。 |
| Input / Output | 数据角色。具体的数据资源和交付合同承担存储、交付、访问与回收。 |

现行 `Unit` 调用面包含 Team 和 Task，内核例程通过 Kernel Team 创建内部 Task。现行 `View.Clone` 提供有界复制交付，源码中也仍有 `View.Share`，包括特定来源的派生与观测入口。本文用 Unit 指独立控制流，用 Copy 指复制交付职责。普通共享依赖 Nest 和 Pend，现行调用与专用观测入口的迁移范围仍需推导。[Unit 调用](../../api/src/abi/call/unit.rs) · [Clone 调用](../../api/src/abi/call/view/clone.rs) · [Share 调用](../../api/src/abi/call/view/share.rs) · [现行内存合同](../../api/memory.md)

## 三、设计不变量

1. **位置唯一。** 一个 Unit 同时最多占用一个 Hart，一个 Hart 同时最多承载一个已派发 Unit。在可观察的提交边界，就绪、等待和占用 Hart 互斥。若用过渡记录衔接交接，该记录须有唯一持有者，且不能被重复消费为可派发资格。
2. **提交匹配本次实例。** 派发、等待裁决、撤回和完成证据须绑定准确的身份与操作。若使用可复用槽位，须说明如何拒绝过期引用。快照、队列索引和调度提示只辅助定位，提交时仍须核对当前有效状态。
3. **终结关闭正常派发。** Unit 一旦接受结束决定，运行中的控制流须前往安全交接点。只有离开执行位置并结清该 Unit 的必需退出义务后，才可发布完成。结果记录可在之后单独回收。
4. **等待只结清一次。** 通知、超时、取消与来源关闭竞争同一次登记。只有匹配当前票据的胜方可以提交结清，Room 仍须确认 Unit 允许重新就绪。
5. **通知只说明事件。** 一次通知可覆盖多个请求。处理完成、结果可领取、映射已撤回、存储可复用，分别依赖实际所有者提供的证据。
6. **共享访问保持唯一的物理归还责任。** 多个 Nest 可分别保留同一 Cell 的访问。授权关闭须与新的映射提交串行。地址与物理存储都要等相关映射和硬件义务结清，才按各自条件复用。
7. **义务与成本有界。** 可能产生外部效果前，应落实失败责任并保留恢复容量。登记、积压数据、在途操作和保留结果须有可计费的上限，Work 的单轮推进、重试与清理也须有界。[目标内存模型](../design/memory/model.typ)

## 四、生命周期

### Unit 的身份与 Room 的位置

候选主生命周期为 `Live → Ending → Completed`。**Live** 期间，Room 可令 Unit 处于尚未派发、就绪、运行、等待或暂停等位置。**Ending** 关闭正常派发，现任 Hart 仍可能保有架构现场，直到安全交接。**Completed** 表示必需退出责任已经结清，终结记录可被观察并按其合同单独删除。退出、故障与取消如何确定唯一结束决定，以及结果记录的可见期限，仍需明确。

候选创建协议先准备 Nest、入口、栈和所需的数据访问，再在发布边界复查身份、权限和 Nest 的接入状态。创建与首次派发各自提交。现行 ABI 14 由调用方在目标 Nest 准备启动数据和栈，Task 创建时为休眠，随后由 Resume 获得执行资格。[现行 Task 启动合同](../../api/task.md)

长期 Work 的典型位置变化是「就绪 → 运行 → 等待 → 就绪」。一次唤醒让同一 Work 重新参与调度。一次运行可以处理一项或推进一批有界工作。

### Input、Output 与一次操作

| 数据角色 | 存续边界 |
| --- | --- |
| 创建时的 Input | 创建合同提供初始值或既有数据的访问。Unit 使用完毕即可释放本次关系，底层存储由原所有者按合同回收。 |
| 运行中的 Input | 独立交付。小数据可按值或用 Copy 交付，大数据可交付描述符，并在接收方 Nest 中建立受授权的映射。描述符只描述数据的位置和范围。 |
| 单次操作的 Output | 操作所有者先确定结果及其保留责任，再发布结果。交付合同规定领取、保留期限、放弃与回收。Work 可继续处理下一项。 |
| Unit 最终的 Output | 可为内联数据或对既有资源的引用。Unit 完成可被观察前，必须已落实 Output 的保留责任。观察者按交付与授权合同获得数据。 |

一次请求可用「待领取 → 已领取 → 处理中 → 成功或失败」推导责任。待领取时，交付方保留输入；撤销待领取输入与领取本身须有明确的提交顺序。领取后，操作所有者接手处理。生产者退出不会逆转已提交的领取。如果处理已经产生部分资源转移、映射发布或硬件效果，由操作所有者决定回滚、补偿、保留中间状态重试或结算失败。重新入队需要先证明操作可以安全重放。

已交付副本按接收方合同独立存续。依赖共享映射的操作则须约定需要保留的访问、撤权可见性，以及无法继续时由谁结算。生产者退出可以触发撤权，已发生的效果与对应退役义务仍须结清。Input 和 Output 与 Unit 可以有不同的存续期，其身份沿用真实数据资源，无需额外的 `InputId` 或 `OutputId`。

## 五、交接协议

以下是候选顺序。提交点、失败时的可观察状态和后续责任必须能逐项核对。

### Room 与 Hart / Metal

1. **选择。** Room 根据就绪位置、Hart 参与状态与调度预算等事实选择继续、改派或进入空闲。提交前核对 Unit 身份、资格、位置及目标 Hart 的有效性。
2. **移出与交入。** Room 结清旧占用的调度记账，确定旧 Unit 重新就绪、等待、暂停或进入退出处理。被选中的下一 Unit 从可派发位置交给目标 Hart。提交须共同约束旧位置、目标槽与新位置，避免两处同时持有可派发资格。
3. **切换。** Metal 在陷入或等效安全边界保存所需现场，根据已提交的选择恢复对应上下文，并执行 Nest 及架构所要求的转换或同步。若 Room 先发布位置，协议须保留明确的在途责任，阻止旧现场尚在使用时的迁移、重新派发或回收。
4. **失败。** 提交前若位置、资格或 Hart 状态已失效，撤销未发布准备。进入硬件交接后若无法确认完成，继续保留现场与义务，由指定责任方恢复或推进停机。具体安全边界需要 RV64 验证。

当前实现同时在 Task 执行状态与 Room 调度槽中协同维护执行事实。本文的逻辑归属允许复用现行字段及同步边界。[Room 调度槽](../../server/src/basis/room/scheduler/slot/mod.rs) · [Task 执行状态](../../server/src/basis/unit/task/execution/mod.rs) · [Hart 状态](../../server/src/metal/riscv/hart/) · [Metal 切换路径](../../server/src/metal/riscv/switcher/)

### Sign 与 Room

1. **检查并登记。** 条件已满足时可立即继续。否则准备票据、来源登记和超时资源，并与 Room 的离核提交衔接。用同一提交边界或等价的重查协议覆盖条件变化与登记之间的竞态。准备失败时撤销未发布登记并保留原位置。
2. **裁决并交接。** 事件、超时、取消和来源关闭竞争同一张票据。胜方移除或使其余登记失效，并把匹配本次等待的结果交给 Room。Room 核对当前位置与当前派发资格，再提交就绪。若 Unit 正在终结，只结清等待义务。
3. **恢复并重查。** Unit 获得 Hart 后读取等待结果，再向来源重查可领取状态。超时结束该次等待，源操作是否取消由其合同决定。合并或迟到的通知可通过同一重查流程处理。

本文的通用等待裁决是协议层概念。现行 `Sign.Await` 还有服务绑定和调度准入条件。[Sign 调用](../../api/src/abi/call/sign.rs) · [等待交接实现](../../server/src/basis/sign/wait/block.rs)

### 向 Kernel Work 交付请求与结果

1. 生产者 Unit 经 Copy 发布小输入的独立副本。大输入可 Copy 描述符，由有效 Pend 授权 Work 在自己的 Nest 建立针对原存储的映射。Work 必须核对映射、有效范围和数据就绪条件。描述符提前到达、映射失败或撤权都应有可结算的结果。
2. 数据可领取后，生产者通过 Sign 通知 Work，或由可重查的来源条件触发唤醒。通知触发失败或合并时，已提交的数据继续由交付方持有。协议须通过保留通知、原子重查或有界重试避免 Work 永久等待。
3. Work 由 Room 派发后向实际所有者领取。领取提交确定副本的去向与操作责任。达到容量限制时，服务可按合同拒绝、施加背压、合并等价请求或仅保留最新状态。需要逐项交付的请求必须得到明确的保留或拒绝结果。
4. Work 推进有界步骤并在操作所有者处保留进度。发布结果前先落实保留或交付责任，发布后才通知观察者。Work 退出时，关闭接收与最后一次发布须串行，已领取操作要么结清，要么移交给明确的责任方。

现行内核例程可用于核对有界推进、等待和责任保留。长期 Work 的通用请求合同仍需验证。[生命周期清理](../../server/src/entry/work/lifecycle/mod.rs) · [退役推进](../../server/src/entry/work/retirement/mod.rs)

### 从 Pend 撤权到 Nest 退役

发布映射前要复查源区间和目标地址的有效授权、访问模式及映射预算。发布后，Nest 须能依据对应的授权或资源依赖定位映射。撤权先关闭基于该分支的新准入，再撤回相应的既有访问并等待适用的 CPU 或 I/O 完成证据。一条映射的结清只解除其自身义务，其他有效映射与原持有责任按各自合同存续。[Pend 调用](../../api/src/abi/call/pend.rs) · [现行内存一致性与退役](../../api/memory.md#coherence-and-retirement)

## 六、候选数据结构

以下 Rust 片段用来推导状态互斥与字段归属。类型名是占位，其分配、锁顺序、布局和接口均未定稿。

```rust
// 讨论草案，省略标识、票据、结果与容器的定义。
struct UnitRecord {
    id: UnitId,
    lifecycle: Lifecycle,
}

enum Lifecycle {
    Live,
    Ending(End),
    Completed(End),
}

enum End {
    Returned(OutputValueOrReference),
    Faulted(Fault),
    Cancelled(Cancellation),
}

enum Placement {
    Inactive,
    Ready,
    Running(HartId),
    Waiting(WaitTicket),
    Detached,
}
```

- `UnitRecord` 表达 Unit 身份和生命周期，`End` 表达唯一的结束决定。`Ending` 和 `Completed` 即使共用表示，也需要分别说明结果的可访问条件。
- `Placement` 表达 Room 的位置。`Inactive` 和 `Detached` 暂用于推导初始、暂停与退出离核的区别。具体状态数量、Hart 槽的关联与在途表示取决于交接证明。逻辑拆分允许字段与锁共用现有存储。
- `WaitTicket` 代表 Sign 的一次登记。候选关联信息包括 Unit 身份、来源及该次等待的标识，Room 引用它以核对当前位置。Metal 保存现场与硬件交接所需的数据。
- Copy 的候选交付记录可以保留副本资源、容量占用与领取状态。若采用一次性交付，由具体服务保留待领数据。Nest 保存映射的访问与退役记录，Pend 管理授权来源。

## 七、未决问题与验证条件

| 未决问题 | 需要验证的条件 |
| --- | --- |
| Unit 与 Room 的状态如何协同提交，现行 Task 和 Team 如何演进？ | 对照创建、暂停、恢复、抢占、退出与观察。验证终结与派发竞争、重复请求和槽位复用下的位置唯一及结果稳定。 |
| Hart 加入、退出、迁移与空闲如何交接？ | 明确参与、下线和退回空闲的条件，给出架构现场的交接点和在途失败责任。在 RV64 多 Hart 场景核对旧现场、页表与栈的安全复用。 |
| Sign、Room 和来源如何共同结束等待？ | 枚举发布与登记交错、重复通知、超时、取消、来源关闭和 Unit 退出。验证无丢唤醒，且过期票据不能再次令 Unit 就绪。 |
| 长期 Work 的 Copy 是有界排队交付还是一次转移？ | 本分支的内存设计给出 Copy 持有队列和交付状态的路径，其通用性仍需校验。明确待领持有者、领取顺序、多接收方竞争、确认、容量和关闭。验证失败后的保存与重放不会丢失请求或重复执行。 |
| Nest 如何覆盖不同共享拓扑？ | 先验证由一个 Flat 持有 Cell、多 Nest 映射该区间的路径。若不同 Flat 需要引用同一 Cell，需区分引用与唯一物理持有，并验证别名属性、修改、撤权和回收。现存 Share 专用入口也需另行核对迁移合同。 |
| Input / Output 的存续和操作结算如何落实？ | 明确初始 Input 在创建后是否保留，定义领取提交点、结果可领取期限、消费者退出后的回收与授权撤销后的处理。验证部分效果仍有可恢复的责任记录。 |
| Work 如何在故障、失去执行机会或停机时结清？ | 明确关闭准入、排空或可靠移交的次序，给出服务预算、进展条件与重复执行规则。用退出清理和内存退役验证兜底路径。 |

状态转换、权限边界和故障注入可由相应所有者在 Host 检查。陷入、恢复和跨 Hart 架构效果需要 RV64 目标执行，设备退役由其后端的完成证据证明。候选协议目前仍待这些验证。[Kernel 验证指南](../../server/tests/README.md)
