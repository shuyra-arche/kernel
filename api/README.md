# kernel-api candidate

This directory is an isolated M1 candidate, not a production package and not a
canonical source switch. It exists to test whether the existing `env` and
`wire` crate identities can be exposed through one candidate path without
copying either implementation.

## What this package is

- Package `kernel-api` 0.1.0, edition 2024, `publish = false`.
- Own `[workspace]`, so it is independent of the enclosing `kernel` workspace.
- `#![no_std]` library.
- Exactly two transparent re-exports:

  ```rust
  pub use env;
  pub use wire;
  ```

- No types, wrappers, forwarding functions, copied implementations, ABI
  changes, or codec changes are defined here.
- No `std`, runtime, entry point, panic handler, allocator, or linker script is
  added.

The two `wire` names stay distinct on purpose:

- `kernel_api::env::wire` is the existing register/ABI wire vocabulary owned by
  `env`;
- `kernel_api::wire` is the standalone byte/protocol codec crate.

`kernel_api::env::*` and `kernel_api::wire::*` are temporary candidate paths,
not the final migration names.

## Macro boundary (narrowly probed)

The existing `mold` macros keep their hardcoded legacy paths:

- `Envcall` emits references such as `crate::wire`;
- `Frame` defaults to `::env::wire` unless `#[frame(codec = ...)]` is used;
- `interface` / `contract` use `::env` and `::wire`;
- `entry` hardcodes `execution::boot::entry`.

A re-export cannot make those paths path-agnostic. This candidate therefore
makes no general macro-portability promise. Root external probes establish only
these narrow facts:

- default `#[derive(Frame)]` with only `kernel_api` and no direct `env`
  dependency fails with `E0433`, as expected from the `::env::wire` default;
- the same default `Frame` succeeds when direct `env` is available;
- explicit `#[frame(codec = kernel_api::wire)]` succeeds;
- a contract-macro fixture with canonical direct `env` / `wire` dependencies
  runs 3 passing tests covering `Frame`, `WireCodes`, `contract`, and
  `interface`.

These probes do not establish full macro compatibility, path-independence, or
that macros work without the legacy aliases. If macro consumption is tested
separately, add the exact `mold` pin
`f52501f4c91b686eded8b4bcd743b4e96084b7f9` and preserve the legacy crate
aliases (`env`, `wire`, and the macro's expected `crate::wire` shape). `mold`
`entry` is explicitly excluded: entry assembly belongs to a future kernel-rt
scope, not to this API candidate.

## Verification

Run these portable commands from this repository's `api/` directory (`cd api`
from the repository root). Cargo picks up the repository's pinned nightly
toolchain from the parent `rust-toolchain.toml`. `Cargo.lock` has already been
generated, so every build command below uses `--locked`.

```sh
cd api

# Verified host tests: 5 passing.
cargo test --locked --target x86_64-unknown-linux-gnu

# Verified RV64 no_std library check.
cargo check --locked --lib --target riscv64gc-unknown-none-elf

# Dependency graph and metadata; metadata is intentionally without --no-deps.
cargo tree --locked --target x86_64-unknown-linux-gnu
cargo metadata --format-version 1 --locked

# Offline reproduction of the same checks.
cargo test --locked --offline --target x86_64-unknown-linux-gnu
cargo check --locked --offline --lib --target riscv64gc-unknown-none-elf
cargo tree --locked --offline --target x86_64-unknown-linux-gnu
cargo metadata --format-version 1 --locked --offline
```

The supported and verified targets are `x86_64-unknown-linux-gnu` and
`riscv64gc-unknown-none-elf`; both are 64-bit. The original `env`/`wire` codec
quirks are untouched by this candidate, and no 32-bit correctness claim is
made.

Expected checks:

- `tests/env_identity.rs`: old `env` types and candidate-path types round-trip
  by assignment in both directions, and old `Wire` / `FailCode` trait bounds
  accept values through the candidate path.
- `tests/wire_identity.rs`: old `wire` `Field`, `Span`, `Message`, and
  `Contract` remain the same traits when reached through `kernel_api::wire`.
- `tests/abi_contract.rs`: representative permission rejection, memory failure
  codes, a Unit call slot, and `ReferenceRange` byte width/order keep the
  values asserted by the existing `env` host tests.
- The RISC-V check must show a dependency graph containing only `env`, `wire`,
  and their existing transitive dependencies, with no `execution`, `std`,
  runtime, allocator, entry, or linker machinery from this candidate.

## Known limits

- Host tests prove type/trait identity and host-side codec behaviour. They do
  not prove a real syscall/trap path.
- The candidate is not a published package and does not switch any consumer,
  lockfile, or canonical dependency source.
- Macro compatibility, final naming, and `std`/`rt`/kernel-rt layering remain
  separate review and implementation steps.
